# CHANGELOG MODULE BEEZCRM FOR [DOLIBARR ERP CRM](https://www.dolibarr.org)

The version of the module is the `$this->version` property of `core/modules/modCrm.class.php`. This file is shown by Dolibarr on the help page of the module (Home → Setup → Modules, help icon of the CRM line). Newest version first. A change a user or an administrator can notice goes here, in the same change.

## 1.2.0 (2026-11-13)

This version improves the salesperson's workflow and connects the CRM deals to the prospects and customers (third parties, "tiers") of Dolibarr.

Documentation rule for this version: whatever changes an interface or the data is added to `doc/USER_GUIDE.md`, `doc/ADMIN_GUIDE.md` and `doc/STRUCTURE_ANALYSIS.md` marked **From v1.2.0**, so the guides do not read as if it had always been there. Each change is listed below in the same change that builds it.

### Added

- **The module is called BeezCRM.** The name shown in Dolibarr (module list, setup page) is now "BeezCRM", and the module has an official logo (`img/crm.svg`, `img/crm_logo_512.png`, used as the module picto `crm@crm`). The menus, the permissions and every other label keep saying "CRM", and the technical name stays `crm` (folder `custom/crm`, tables `llx_crm_*`, constants, rights, MCP tool names): nothing to migrate.
- **Outside agents and assigned steps.** New rights **`assigned`** (read the deals that have a step assigned to me), **`note`** (add and edit own notes) and **`mystep`** (create steps for myself or the owner, change and complete my own steps) make the profile of an outside agent who phones the prospects, with no right on Third parties. The agent sees only Home (their steps to do) and Activities (their steps) and opens a deal only while one of their steps is not done; the card shows the contact's phone, mobile and e-mail as text and no link to the third party. A step now has an **Assignee**: a field in the create form (the owner of the deal by default; the agent can only choose themselves or the owner), in the edit form for the salespeople, and a column in every table of steps; the assignee is told by e-mail (`CRM_ASSIGN_NOTIFY`, following the reminder dry-run). MCP tools follow the profile (`assignee_id` in `create_crm_activity` and `update_crm_activity`). **Re-enable the module** after the update (new rights and menus). New check: `test/cli/agent_check.php`.
- **Attach files to an e-mail of the editor.** The e-mail editor (`email_compose.php`) has an **Attachments** row: choose files (several at once; the Dolibarr document size limit per file, 10 files and 20 MB at most per e-mail), tick "remove" to take one off. They are kept with the draft when you save it, **sent by Dolibarr with the message** when you press Send, and **kept on disk** (`<documents>/crm/opportunity/<deal id>/mail/`) so that the **Message history** of the deal shows them under the message, to download (a magnifier previews a PDF). They follow the message when the draft is replaced by the sent e-mail (also for "E-mail sent manually"), and go with a discarded draft or a deleted deal. A file that cannot be kept stops the send. **Schema version 8** (table `llx_crm_mail_file`): disable and re-enable the module after the update. New check: `test/cli/mail_attachments_check.php`.
- **From the history to the text of an e-mail.** An e-mail line of the deal's **History**, of the **CRM history** of the Prospect tab, of the **Next step** list (a past e-mail, even one only marked as done) and of **Activities** now leads to the text of that message in the **Message history** of the deal card, which opens it and scrolls to it. No agenda right is needed (the link to Dolibarr's own agenda card did not show the text of an e-mail). New MCP tool `list_crm_opportunity_messages` (the e-mails of a deal with their text).
- **A completed draft is no longer shown as a sent e-mail.** A planned e-mail that was only marked as done (the check icon) now appears in the Message history, the History and the CRM history with the badge **Draft closed** (in yellow) instead of "E-mail sent", with its text and no addresses. MCP `list_crm_opportunity_messages` returns the direction `closed_draft` for it.
- **Delete an automated outreach completely (administrators).** For the cleaning of tests, a user who may configure the CRM (right "Configure CRM") has **Delete the outreach completely** on the outreach card: its steps, its enrolments and its journal are deleted after a confirmation that gives the counts and warns about running enrolments; the agenda events it made on deals (drafts, e-mails sent) and the deals stay. A trash icon deletes **one enrolment** with its journal lines. MCP: `delete_crm_sequence` (right to configure the CRM), which is **not offered unless an administrator switches on** the new setting **"Allow MCP tools that delete CRM records"** (`CRM_MCP_ALLOW_DELETE`, off by default, asks for a confirmation when turned on, and cannot be read or changed through MCP). It is the general switch of **every** `delete_*` MCP tool (`delete_crm_opportunity`, `delete_crm_stage`, `delete_crm_activity`, `delete_crm_sequence`, `delete_crm_sequence_step`, `delete_crm_note_file`): with it off, the default, none is listed and each refuses a call. **This changes the earlier tools**, which were always offered to a user holding the right. New check: `test/cli/outreach_delete_check.php`.
- **Internal reference on the deal.** A new field **Internal reference** on the deal (create and edit forms, deal card): the number of the task in another system (up to 128 characters). A new setting **Web address of internal references (prefix)** (`CRM_INTERNAL_REF_URL`, CRM → Setup → Parameters, an http or https address such as `https://tracker.example.com/browse/`) turns the reference into a link, the address followed by the reference, opened in a new tab (`target="_blank"`, `rel="noopener noreferrer"`); without it the reference is plain text. The reference is found by the search of the opportunity list. MCP: `internal_ref` in `create_crm_opportunity`, `update_crm_opportunity` and `get_crm_opportunity` (which also returns `internal_ref_url`). **Schema version 7** (column `ref_internal`): disable and re-enable the module after the update. New check: `test/cli/internal_ref_check.php`.
- **Message history on the deal card.** A new section **Message history** lists every e-mail of the deal, oldest first: sent from the editor, by an automated outreach, from a mail program with the archive address in copy, and the answers of the prospect, each with its direction, date, subject, addresses and text (**read** / **show all**). The text is read with the CRM's own right on the deal. This is the place to see what the e-mail collector found in the archive mailbox.
- **Discreet deal marker in e-mails.** The marker is now short, `[O2026-0001]` instead of `[OPP2026-0001]` (the old form is still recognised), and **nothing adds it automatically any more**: not to a draft, not to the subject of what is sent, not to the **Open in my mail client** link. What is typed in a title is kept as typed. A message written in a mail program is tied to its deal by the address of its contact; the editor tells the person to type the marker themselves when the contact has several open deals. A message sent by the platform (**Send from here**; the outreach never had one) no longer shows any marker in its subject: the deal is in its headers (`Message-ID`, `X-Dolibarr-TRACKID`), which the answers keep through `In-Reply-To` and `References`. A message written in a mail program is found by the marker, or by the address of the contact. No schema change. New check: `test/cli/messages_check.php`.
- **Internal notes are agenda events.** Every internal note is also recorded as a done agenda event **"CRM note added"** (type "Other", no new event type), linked to the deal and to its third party, in the name of the author and dated like the note, with the text of the note: the notes show in the agenda of the third party. Editing a note updates its event. The **History** of the deal card is now the whole story of the deal, oldest first: stage moves, done calls, meetings and e-mails, and the notes (with the beginning of their text); the **CRM history** of the Prospect tab shows the notes too. The note events are not listed among the next steps and do not restart the "rotting" clock of a deal. Existing notes get their event when the module is enabled again. **Schema version 6** (column `fk_action` of the notes): disable and re-enable the module after the update, see `UPDATE.md`. Tests added to `test/cli/notes_check.php`.
- **Categories of the accounts, with colours.** The CRM uses the categories of Dolibarr's Tags/Categories module (Customers/Prospects), with their **colour**: the account name is underlined with the colours of its categories (a band per coloured category, three at most) on the kanban cards, in the opportunity list and on the deal card, which also shows the labels as coloured badges and the language of the account (FR, NL...). A pencil on the deal card chooses the categories of the account, by checkboxes, and by radio buttons for the groups declared in the new setting **Mutually exclusive category groups** (`CRM_CATEGORY_SINGLE`, check boxes, with a line of explanation under its name), such as a degree of interest (Hot, Warm, Cold). The list and the kanban have a category filter. It needs the CRM right to write deals and a deal the user may see, and no Dolibarr right on categories (give the salespeople **Read categories** only). MCP: `categories` in `get_crm_opportunity`, `category_id` in `list_crm_opportunities`, new tool `update_crm_opportunity_categories`. No schema change. New check: `test/cli/categories_check.php`.
- **Time of a next step.** The mini-form that creates a next step (deal card, section **Next step**) now asks for the hour and the minutes as well as the date, with Dolibarr's date and time component (minutes by 5), and proposes tomorrow at about the same time (to the nearest 5 minutes). The edit form uses the same component.
- **"Not interested" link in every e-mail.** Every e-mail sent for a deal (from the editor, by an automated outreach, or written with the AI assistant) ends with the link **"Not interested, don't contact me again soon."** (in the language of the contact of the deal, else of its third party, else the current language), added when the message is sent; the editor shows it under the text; it is also added to the text of "Open in my mail client" and "Copy text". The link opens a **public page** (`optout.php`, no login) with a confirmation button; once confirmed, the deal is **closed as Lost** with the new loss reason **Not interested**, a done event is added to the deal, the running outreach of the deal stop, and the prospect sees a confirmation. The page takes one parameter only, the hash (64 hex characters, an HMAC that cannot be guessed; only its SHA-256 is stored), refuses anything else, shows no data, starts no session and sets no cookie. Setting **"Ask the prospect to confirm"** (`CRM_OPTOUT_CONFIRM`, on): off records the request as soon as the link is opened, which mail scanners would trigger. **Schema version 5** (table `llx_crm_optout`, loss reason): disable and re-enable the module after the update; make sure `custom/crm/optout.php` is reachable by prospects without a login. New check: `test/cli/optout_check.php`. **The editor has a box "Add the 'not interested' link at the end of this e-mail", ticked by default,** to send one message without it when the prospect has already answered; it applies to that message only (also to "Open in my mail client" and "Copy text"), a saved draft keeps it, and automated outreach always keeps the link.
- **Internal notes instead of the description.** The deal card has a section **Internal notes**: the notes are in chronological order, right under the data of the deal: only the latest is shown, and the link **Show the n earlier notes** unfolds the others above it. The form to add a note is below the list. Each note keeps its author, its date and time and its text. A note can be **edited** later (by its author, or by a user who reads every owner's deals); every earlier text is kept, with who wrote it and when, under a **history** link. Files can be attached to a note (several at once; the Dolibarr document size limit, at most 10 per note), downloaded by clicking the name, and previewed when they are PDF with the magnifier icon, in a window of the page itself; a **paperclip** next to the title opens the list of all the files of the deal with their size, date, author and note. Files are stored in the Dolibarr documents directory under `crm/opportunity/<deal id>/` (back it up) and are served only to users who may read the deal. The existing descriptions become the first note of their deal. New MCP tools: `list_crm_opportunity_notes`, `list_crm_opportunity_files`, `list_crm_note_versions`, `add_crm_opportunity_note`, `update_crm_note`, `add_crm_note_file`, `delete_crm_note_file`; `get_crm_opportunity` returns `notes` instead of `description`, `create_crm_opportunity` puts its `description` in the first note, `update_crm_opportunity` no longer takes one. The AI reply prompt sends the latest three notes. **Schema version 4** (three new tables, the descriptions copied to notes): disable and re-enable the module after the update, see `UPDATE.md`. A file that cannot be saved now says why (antivirus, directory not writable, PHP temporary folder...) and the cause is written to the Dolibarr log (`CRM note file ... not saved`). New check: `test/cli/notes_check.php`.
- **The CRM on the Prospect tab of a third party.** The **Prospect** tab of a third party (`comm/card.php`, not the **Third party** tab) shows a line **CRM opportunity** in its table of data, with a link to each of its deals in the CRM (three at most, open first), or a **New opportunity** link for a prospect that has none. At the bottom of the right column, a block **CRM history** lists the last 5 events of its deals (stage moves, done steps and e-mails), with a link **Full CRM history** to a new page (`account_history.php`). Only deals the user may read are shown; nothing shows when the module is off. New hook context `thirdpartycomm`: **disable and re-enable the module** after the update. No schema change, no new right. New check: `test/cli/account_view_check.php`.
- **E-mails to or from the deal contact are recorded without a marker.** When the archive (lead collection) mailbox receives a copy, in Cc or Bcc, of a message with no tracking id, thread or `[OPP…]` reference in its subject, it is now recorded in the history of the deal if the other end is clearly the contact of that deal: the sender of a received message, or a To/Cc recipient of a message sent by us, has the e-mail address of the deal contact. Only open deals are considered, and when the contact has several open deals nothing is attached (use the reference in the subject). The sender, authentication and automatic-mail checks of 1.1.0 still apply, so a received message from the contact also stops the outreach and moves the deal to the reply stage. No setting, no schema change. New check: `test/cli/mail_contact_match_check.php`.

- **Rate limit and discreet logs for the public "not interested" page.** `optout.php` now counts the requests of each address (files under `<documents>/crm/optout_limit/`, no table): over **120 requests or 10 unknown links per 10 minutes** it answers **429 Too Many Requests** with `Retry-After` (constants `CRM_OPTOUT_RATE_WINDOW`, `CRM_OPTOUT_RATE_ALL`, `CRM_OPTOUT_RATE_FAILS`, 0 turns one off). The module logs only the **last 4 characters** of a link. The link of an HTML e-mail carries `rel="noreferrer noopener"` and `referrerpolicy="no-referrer"`. The administrator guide gives nginx and Apache configuration (rate limit, an access log that does not keep the token, real address behind a reverse proxy) and a fail2ban jail. The documents folder must be writable by the web server, as for the notes. New checks in `test/cli/optout_check.php`.

### Fixed

- **"Save draft" did not keep the sender choice.** The sender chosen in the e-mail editor is now remembered when you save the draft (it was only remembered on send), so reopening the draft shows it. It is kept per user, as before: the last choice made is the one proposed, not one per draft.
- **The "not interested" link used the language of the third party, not of the contact.** The text of the link (in the e-mail editor, its preview and every e-mail sent) is now in the language set on the **contact** of the deal; when the contact has none, the third party's, then the current language.
- **The hour proposed for a next step was the UTC one.** Dolibarr shows times in the time zone of the browser (`MAIN_TZUSERINPUTKEY = tzuserrel`) taken from the login form into the session; a session that has none, or UTC because the browser did not say (some browsers and privacy settings report UTC), shows UTC. The CRM pages now give such a session a real zone: first the one the browser reports in a cookie (`crm_tz`, only a real time zone name is accepted, one automatic reload of the page), else the new setting **Default time zone of the users** (`CRM_DEFAULT_TIMEZONE`, for example `Europe/Brussels`, empty by default). A session that already has a real zone other than UTC is not touched. The next-step form tells which zone the times are shown in. The CRM pages also use the zone of the session **whatever the global Dolibarr setting `MAIN_TZUSERINPUTKEY`** (set in memory for the request by `crmStartPage()`), so a server where that setting was never made no longer shows UTC in the CRM. New check: `test/cli/timezone_check.php`.
- **"Save the draft" did not save an e-mail text edited in the HTML editor.** A JavaScript error when the e-mail editor opened (it looked for an element, `crm-plain-note`, that the page no longer had) stopped the editor from hiding the pane that is not in use: on a draft stored as plain text, the HTML editor and the plain text box were both shown while the format stayed "plain text", so a change made in the HTML editor was ignored on save and the old text was kept. The element exists again, the script no longer fails without it, and the plain-text pane alone is shown for a plain-text draft. Switching to HTML, editing and saving now keeps the new text (tested in a browser).
- **"Propose a reply with AI" gave a 500 error** (`Call to undefined function dol_set_user_param()`) on installations where Dolibarr had not already loaded `core/lib/functions2.lib.php` for the request. The AI call counter and the remembered sender choice of the e-mail editor now load that file themselves.

## 1.1.0 (2026-10-18)

### Security

A review against the OWASP Top 10 led to these changes. Nothing in the data model changes.

- **CSRF.** Every action of every page now needs the token of the session, not only the actions Dolibarr's own check sees. A link such as `email_compose.php?act_send=1` no longer sends anything: the buttons of the e-mail editor are read from a POST only.
- **Who sees what.** The enrolments and the journal of an automated outreach are limited to the deals the user may read (own deals, or all with "Read all"), and to the current entity. Stopping an enrolment or marking a reply checks the deal too; marking a reply moves the deal only for a user who may write.
- **Enrolment rules in one place.** `Sequence::enrol()` now refuses an inactive outreach, a deal that does not exist, a closed deal and a deal that already follows an outreach, whichever entry is used (deal card, outreach card, MCP).
- **Inbound e-mail is no longer trusted blindly.** A message found by a deal reference or a Message-ID is kept only if its sender (received) or one of its recipients (sent by us) is an address the deal knows: its contact, the other contacts and the address of its third party, or a colleague at their company domain (public mail domains such as gmail.com do not count). A message that our mail server reports as failing SPF/DKIM/DMARC is ignored; the new setting **"Archive only authenticated e-mails"** (`CRM_ARCHIVE_REQUIRE_AUTH`, off by default) also ignores a message without a passed check. An automatic message (bounce, out-of-office, list) is kept but no longer stops the outreach or moves the deal. Dates are kept within a believable range and long headers are cut.
- **Stored XSS.** Titles and confirmation texts that print a deal, outreach, stage or list label are escaped; the MCP tools strip markup and line breaks from labels, references, subjects and codes, strip markup from descriptions and notes, and clean the HTML of an e-mail step; the web forms apply the same rules when saving. The editor's "has text" test no longer builds live HTML.
- **Mail header injection.** The subject, recipient and sender of every e-mail are made single-line before they are sent, and the sender and archive addresses are validated when saved.
- **Links of a deal are validated**: the third party and the contact must exist in the entity and the contact must belong to the third party; a proposal can be linked only if it exists, the user may read proposals and it belongs to the third party of the deal. A closed deal can no longer be reopened without a next step when that rule is on.
- **Settings are validated** on the setup page (switches 0/1, bounded numbers, known modes, one valid address, bounded AI prompt), all values before any write. The MCP tool `update_crm_settings` is **removed**: an AI assistant can read the settings (`get_crm_settings`) but cannot change them, since a setting such as dry-run or the sender decides whether real e-mail leaves. Stage values are validated too (colour `#rrggbb`, probability 0–100, forecast category); the MCP stage tool no longer lets a stage change pipeline.
- **AI.** A per-user limit of suggestions per hour (`CRM_AI_MAX_PER_HOUR`, default 30), a cap on the prompt, and a sentence telling the model that the e-mails and notes it reads are data, not instructions.
- **Errors.** A database or provider error is written to the Dolibarr log and an ordinary user sees a generic message; an administrator sees the text, escaped.
- **Concurrency.** The job that sends the outreach claims each enrolment before working on it, so two runs at the same time no longer send the same e-mail twice.
- **Other.** Lists are capped at 500 rows; entity filters were added to the journal and the next-step queries; the class and library files refuse a direct request; a `.htaccess` hides `.git`, `doc`, `test`, `sql` and the other source files on Apache (see INSTALL.md for nginx and production); the inline script of the deal card carries the CSP nonce.

### Automated outreach

- The **deal card** has a section "Automated outreach": the outreach the lead is enrolled in with its status (running, stopped with the reason, done), the step it waits for and when it falls due. A lead that follows none, on an open deal, shows a list of the outreach that can be used (active, with at least one step) and the button "Enrol from now": the enrolment starts at the moment it is saved, the first step is due after its delay counted from then. A lead follows one outreach at a time; it needs the right "Manage automated outreach" to enrol.

### Prospects who reply

- A new stage, **Replied to outreach** (shown in French as "Répondu à approche"), between New and Qualified in the standard pipeline (15%, forecast category `pipeline`). It is the **reply stage** of its pipeline, marked by the new checkbox "Reply stage" of the stage form (one per pipeline; it must be an open stage; copying a pipeline copies the mark).
- When the answer of a prospect is recorded on an open deal, the deal **moves by itself to the reply stage** of its pipeline: when the e-mail collector records an incoming message on the deal, and when someone presses "Mark replied" on an enrolment of an automated outreach (screen or MCP tool `update_crm_opportunity_replied`, which now also moves the deal). The deal moves only when it is still before that stage: one that is already there or beyond it, or won or lost, stays. The move is written in the stage history, and the rule "a next step is required to change stage" does not apply to it. The salesperson then qualifies the deal.
- The setting **"Move a deal to the reply stage when the prospect replies"** (`CRM_REPLY_MOVES_DEAL`, on by default) turns this off; the Parameters tab has it as a switch.
- The explanation at the top of the list of automated outreach now describes them as a process for prospecting at scale that stops at the prospect's reply and hands the deal over to the reply stage.
- The MCP tool `create_or_update_crm_stage` takes and returns `is_reply`.
- Database schema version 3: the column `is_reply` of `llx_crm_stage`, and the stage "Replied to outreach" added to **every existing pipeline that has an open stage and no reply stage** (right after its first open stage), when the module is disabled and enabled again. A new installation seeds it. Nothing else of an existing pipeline is changed, and no deal is moved by the update.

## 1.0.0

First version.

### Sales pipeline

- Deals (opportunities) with several **pipelines**, each with its own stages, probabilities, colours, rotting delays and forecast categories. A pipeline can be created (empty or copying the stages of another one), renamed and deactivated.
- Kanban board with drag and drop, deal and activity lists with filters, sortable columns and paging, and a deal card in the order a salesperson works: details, next step, qualification, stage, proposals, history.
- A short editable **qualification** checklist, **loss reasons** (required to close a deal as lost) and lead **sources**. Stages, qualification items, loss reasons and sources are edited in place in the Setup screen and can be turned off: a turned-off entry is no longer offered but stays on the deals that use it, and an entry that is in use (or a stage that deals have passed through) cannot be deleted, only turned off. Deleting asks for a confirmation. The entries seeded at the first enable are shown in the language of the user.
- **Next steps** are Dolibarr agenda events linked to the deal, and a planned one can be changed (date, kind, title) or deleted from the deal card and by MCP (`update_crm_activity`, `delete_crm_activity`); a done step is history and stays; completing, changing or deleting a step is refused when the deal is not one the user may see; a deal cannot change stage between open stages without a planned next step (setting `CRM_REQUIRE_NEXT_STEP`).
- Proposals of the Proposals module can be linked to a deal.
- Home page work lists (no next step, overdue, past expected close, rotting) and forecast by month and category, a home box, and an entry "CRM opportunities" in the general search box of Dolibarr.
- **Reports**: forecast, cohort conversion from the stage history, win rate, cycle time, loss reasons, by owner, by source.
- A prospect can be created from the deal form (button "New prospect"); the account list is searchable.

### Customer follow-up

- **Automated outreach** (menu CRM → Automated outreach): plans of e-mail, call and task steps, each with a delay counted from the enrolment, enrolled on deals chosen in a searchable list, run by an hourly scheduled job. An outreach and its steps can be created and changed (deleting a step asks for a confirmation and says how many running enrolments wait for it); stop rules (contact replied, deal won, deal lost); journal of every attempt that keeps the e-mail as it was made (placeholders replaced, sender, format), also when it was only simulated or left as a draft, with an icon to open it; the deal card lists the e-mails the outreach made for it, with the outreach, the step and the day of the outreach that caused each one.
- Each e-mail step is a **draft** for the salesperson (default) or is **sent automatically**, per step or by the global setting `CRM_SEQUENCE_EMAIL_MODE`; dry-run for automatic sends and for owner reminders; daily reminder e-mail to the owner of the deals.
- **E-mail editor** (`email_compose.php`): review a planned e-mail, tick "Send me a hidden copy (Bcc)" (on by default) to receive a copy of what is sent, choose the sender address (the default of the CRM, the user's own e-mail, or the mailbox of the lead e-mail collector, remembered per user) and see it before sending, send it from Dolibarr, open it in the mail client, register it as sent, or delete the step. Plain text or formatted (HTML) with an automatic plain-text version. The text of an outreach step has the same two formats.
- **E-mail history**: the e-mails sent through the module are kept on the deal, and the answers are read from a dedicated mailbox by Dolibarr's e-mail collector (operation "CRM: record the e-mail on its deal"). A message is tied to its deal by tracking id, by thread, or by the deal reference in square brackets in the subject. A reply stops the running outreach of the deal.
- **AI assistance**, off by default (`CRM_AI_EMAIL_ASSIST`) and using the AI module of Dolibarr: a reply proposed from the exchange so far, with an editable prompt, and a button that writes or improves the text of an outreach step. The privacy redaction of the AI module is honoured. The calls to the AI service wait up to `CRM_AI_TIMEOUT` seconds (default 120) instead of Dolibarr's 30, for the CRM calls only, and a failure without any HTTP answer says how long it took and whether it timed out or the connection failed.

### Administration

- Setup screen: parameters (on/off switches saved at once), pipelines and stages, qualification, loss reasons, sources; rights, scheduled jobs and hooks registered at the enable; seeded data inserted once.
- **MCP tools** (50, named like `list_crm_opportunities` or `update_crm_activity`) for an AI assistant, within the rights of the user; they check their own rights, as Dolibarr 24.0.0 does not check the rights a tool declares.
- Explanations of more than 12 words are hidden until the "?" button of the page is clicked; row actions are icons; buttons use the same markup as Dolibarr's own, so the theme styles them alike.
- English and French, and a machine translation (not reviewed by a native speaker) for the other languages Dolibarr supplies. Errors shown by the module are translated.
- Documentation: administrator guide (`doc/ADMIN_GUIDE.md`), user guide (`doc/USER_GUIDE.md`), design record (`doc/STRUCTURE_ANALYSIS.md`), `README.md`, `AGENTS.md`.

### Compatibility

- Dolibarr 24.0.0 and 25.0.0 alpha (tested); 21 to 23 are accepted by the descriptor and have not been tested. PHP 8.1 or later.
- The MCP server and the AI features need the AI module (Dolibarr 24 or later). The MCP tools are named verb first, as the core tools are, so that the tool access screen of Dolibarr classes a tool that changes data as "Modify" and its "View only" preset leaves it out. They are registered the way the 24.0.0 loader requires (checked against a 24.0.0 core and the 25 alpha one).
- Schema: the tables `llx_crm_*` are created at the first enable. The module keeps its own schema version (`CRM_SCHEMA_VERSION`, shown in CRM → Setup → About) and runs the missing numbered steps when it is disabled and enabled again, with a notice to administrators when an update is waiting for that.
