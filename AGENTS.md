# AGENTS.md

Guidance for AI agents working on the **CRM** external module for Dolibarr. Read this first, then `README.md` (overview and links), `doc/ADMIN_GUIDE.md` (install, Dolibarr settings, every setup page, cron, e-mail, MCP, maintenance), `doc/USER_GUIDE.md` (what a salesperson does) and `doc/STRUCTURE_ANALYSIS.md` (design decisions, data model, rationale).

## Environment

| Item | Value |
| --- | --- |
| This module (real path) | `/var/www/dolibarr-crm` — the repo root *is* the module root (flat layout, no nested `htdocs/`) |
| Dolibarr install | `/var/www/dolibarr` (git checkout of upstream `develop`; code in `htdocs/`) |
| Dolibarr version | 25.0.0-alpha (`htdocs/version.inc.php`). Module requires Dolibarr >= 21, PHP >= 8.1 |
| Local PHP | 8.3 CLI. The system `phpunit` needs PHP 8.4, so it does not run here |
| Runtime link | `/var/www/dolibarr/htdocs/custom/crm` -> `/var/www/dolibarr-crm` |
| Instance URL | http://my.dolibarr.net — module pages live under `/custom/crm/` (e.g. `/custom/crm/index.php`) |
| Admin login | `admin` on the dev instance. The password is not written in the repository: ask the maintainer, and never copy credentials into code, docs or commits |
| DB | MariaDB/MySQL, database `dolibarr`, prefix `llx_`, entity 1. Credentials are in `/var/www/dolibarr/htdocs/conf/conf.php` (do not echo them). `root` without password is refused |
| Module state | Enabled on the instance (CRM top menu shows). `doc/STRUCTURE_ANALYSIS.md` still says "not enabled": that line is stale |

`conf.php` sets `$dolibarr_main_document_root_alt='/var/www/dolibarr/htdocs/custom'` and `$dolibarr_main_url_root_alt='/custom'`, which is why the module is served from `/custom/crm/`. `$dolibarr_main_prod='0'` (dev mode, errors visible).

Editing files in `/var/www/dolibarr-crm` is live immediately through the symlink. There is no build step. This directory is a git repository (branch `main`).

Do not edit anything under `/var/www/dolibarr/htdocs` (core). The design rule is: no core patch, no extrafield, no `ALTER` on core tables, no new `llx_c_actioncomm` rows. If a change seems to need one, find another way or ask.

## Dolibarr in a nutshell

- Entry for every page: `main.inc.php` (session, auth, `$db`, `$user`, `$conf`, `$langs`, `$hookmanager`). Core classes are `CommonObject`, `CommonObjectLine`, `DoliDB`, `Form`, `FormCompany`, `ActionComm`, `Societe`, `Contact`, `Propal`, `User`.
- Core directories under `htdocs/`: `core/` (modules, lib, tpl, boxes, triggers), `societe/` (third parties, contacts), `comm/` (propal, agenda in `comm/action`), `projet/`, `ai/` (AI + MCP server), `langs/`, `install/`, `admin/`.
- Modules are classes `modXxx extends DolibarrModules` that declare rights, menus, boxes, cron jobs, hooks, constants and dictionaries. Enabling a module runs `init()` (loads `sql/*.sql`, registers everything); disabling runs `remove()`. Enabled state is the constant `MAIN_MODULE_<NAME>`; test with `isModEnabled('crm')`.
- Permissions: `$user->hasRight('crm', 'read')`. Rights ids are declared in the descriptor and stored in `llx_rights_def` / `llx_user_rights` at enable time.
- Tables are named `llx_*` in SQL files; Dolibarr substitutes the real prefix. Most tables carry `entity` (multicompany); always filter with `entity IN (getEntity('...'))` or `$conf->entity`.
- Strings go through language files `langs/<locale>/<file>.lang`, loaded with `$langs->load('crm@crm')` and used as `$langs->trans('Key')`. Dolibarr caches lang files, so reload the page after edits.
- Hooks: a class `ActionsXxx` named after the module is called for each hook context a module lists in `module_parts['hooks']`. The CRM module uses the context `aimcp`.
- Security conventions: CSRF `token` on every POST (`newToken()` / `checkToken`), `GETPOST('x', 'alpha|int|...')` for all input (never `$_GET`/`$_POST`), `$db->escape()` / `(int)` casts in SQL, `dol_escape_htmltag()` on output, `accessforbidden()` for denied access.
- Cron: `llx_cronjob`, executed by `scripts/cron/cron_run_jobs.php` or the web "scheduled jobs" page. Jobs are declared in the descriptor `$this->cronjobs`.
- AI/MCP: `htdocs/ai/` provides an MCP server. `McpHandler` collects tools and asks modules for more through the `addMcpTools` hook in context `aimcp`. Tools extend `McpTool` (`ai/class/mcptool.class.php`) and implement `getDefinitions()` and `execute()`.
- Core references worth reading before changing behaviour: `htdocs/core/modules/DolibarrModules.class.php`, `htdocs/ai/class/mcptool.class.php`, `htdocs/ai/tools/crud_objects.class.php`, `htdocs/comm/action/class/actioncomm.class.php`, `dev/skeletons/` and `htdocs/modulebuilder/` for idioms.

## What this module does

A sales pipeline: account (`llx_societe`), contact (`llx_socpeople`), **deal** (`llx_crm_opportunity`), proposals (`llx_propal`, many per deal), and agenda events (`llx_actioncomm`) as next steps and history. Nothing from core is copied into private tables. Module technical name `crm`, module number `104801`, rights `10480101`–`10480108`, tables `llx_crm_*`, constants `CRM_*`, MCP tools named verb first with `crm` after the verb (`list_crm_stages`, `create_crm_opportunity`).

Key rules (details in `doc/STRUCTURE_ANALYSIS.md`):

- Probability belongs to the **stage**, not the deal. Moving a deal copies the stage's meaning; there is no per-deal percentage column.
- Pipelines have stages with probability, colour, rotting delay, forecast category (`pipeline` / `upside` / `commit`), won/lost flags and a reply flag (`is_reply`, one open stage per pipeline, "Replied to outreach" by default): when the answer of a prospect is recorded on an open deal (`CrmMailArchive::record()`, `Sequence::markReplied()`), `Opportunity::moveToReplyStage()` moves it there if it is before that stage, whatever `CRM_REQUIRE_NEXT_STEP` says, unless `CRM_REPLY_MOVES_DEAL` is 0.
- Open deals need a future agenda event (`CRM_REQUIRE_NEXT_STEP`, default on). A stage move between open stages is refused without one. Won/lost do not need it.
- Closing lost requires a loss reason from the dictionary. Both won and lost write `date_close` and a stage-history row.
- Reports use `llx_crm_stage_history` (cohort conversion), not column counts. Win rate = won / (won + lost) by close date; cycle time uses won deals only.
- Qualification is a short editable checklist (seed NEED / BUDGET / DECISION / TIMELINE, 25 points each); score is the sum of "yes" points, capped at 100.
- Agenda events link to a deal with `elementtype = 'opportunity@crm'` and `fk_element = <deal id>`, and use existing types `AC_TEL`, `AC_RDV`, `AC_OTH` (`AC_EMAIL` and `AC_EMAIL_IN` for e-mails, active or not, as core does). They are created through `ActionComm`, never by direct SQL, and survive module disable.
- E-mail history: customer e-mails sent for a deal go through `crmSendMail(..., $dealId)` (tracking id `crm<dealId>` in the Message-ID, optional copy to `CRM_ARCHIVE_MAILBOX`) and are stored as done agenda events. Reading the mailbox is the core E-mail collector's job; the module only adds the operation `hookcrmrecordemail` (`ActionsCrm`, class `CrmMailArchive`). Never add IMAP code to the module. Details in `doc/STRUCTURE_ANALYSIS.md` ("E-mail history").
- Outreach e-mail steps are drafts by default (`CRM_SEQUENCE_EMAIL_MODE`; anything but `send` means draft): a planned `AC_EMAIL` event, label = subject with `[<deal ref>]`, note = text, reviewed in `email_compose.php` through `CrmEmailDraft`. Sending, registering a manual send and discarding replace or delete the event (`ActionComm::update` does not write the e-mail columns, so no in-place update and no SQL). `CrmMailArchive` matches an imported message to a deal by tracking id, thread, or the `[<ref>]` in the subject, and replaces a pending outgoing event instead of doubling it.
- E-mail is plain text or HTML, one form only: the plain-text alternative of an HTML message is derived (`crmHtmlToText`), never stored or edited apart, because Dolibarr's `CMailFile` builds it and cannot take another. Anything that reads an event note as text must convert it with `crmHtmlToText()` when `crmLooksLikeHtml()`. Read HTML input with `restricthtml`, plain input with `nohtml`. The ajax `previewtext` action must define `NOTOKENRENEWAL` before the bootstrap.
- AI reply suggestions go through `CrmAiReply` and Dolibarr's `Ai` class; the module never talks to a provider itself. It must honour `AI_PRIVACY_REDACTION` (mask, then unmask the answer), must never save or send what the AI returns, and must list in `doc/ADMIN_GUIDE.md` exactly what is sent. Tests inject a generator callable instead of calling a provider. Every real call to the AI service goes through `CrmAiReply::runWithTimeLimit()`, which raises Dolibarr's 30-second limit for that call only (`CRM_AI_TIMEOUT`); do not call `Ai::generateContent()` from anywhere else.
- Core compatibility: the module is run against the Dolibarr 24.0.0 core and 25 (alpha). Do not call a core method added after 24.0.0 without `method_exists()` or a local fallback (`PrivacyGuard::maskNames()` and the `McpTool` rights and confirmation API are 25 only). The hook `addMcpTools` must put the tools in an array inside `$this->results` (`array(array($tool, ...))`): the 24.0.0 loader skips a bare tool object, core develop accepts both, and a flat list registered no CRM tool at all on 24.0.0. Run `test/cli/mcp_tools_registration_check.php` against each core. Every MCP tool must check its own declared rights (`denyMissingRights()` at the top of `execute()`), because 24.0.0 does not. To test against another core, extract it with `git archive <commit> htdocs` into a scratch directory with its own `conf.php` pointing at a copy of the settings, and run the CLI scripts inside transactions.
- Schema: `sql/llx_crm.sql` creates the tables of a new installation in their final form. A change of the tables is a numbered step: increase `crmSchemaCurrent()` and add the entry to `crmSchemaSteps()` (`lib/crm.lib.php`), run by `modCrm::init()` once per installation through `crmUpgradeSchema()`. A step must be safe on a database that already has its result (look before you change), is never edited once released, and the code must still work before the step has run (`crmStepModeSupported()`), because files are live before the module is re-enabled. `DDLAddField` skips an empty `DEFAULT`, so write such an `ALTER` by hand. The release procedure is in `UPDATE.md`, the installation one in `INSTALL.md`.
- The plain/HTML choice of a text area is `js/crm_format_editor.js` (used by the add-step form of `sequence_card.php`; `email_compose.php` has its own inline copy of the same logic, keep them in step). A page using it must handle the ajax action `previewtext` and define `NOTOKENRENEWAL` for that call before the bootstrap. Values inserted into an HTML body must be escaped.
- A link that triggers an action (not just display, list, create or edit) must carry `token=<newToken()>` in its URL: Dolibarr's CSRF check at its default level 3 drops the action of a GET without a token. Forms carry it as a hidden field. A step is changed with `Sequence::updateStep()` (position kept, enrolments untouched).
- Explanations: any text that explains rather than labels, warns or reports is printed with `crmHelp($html, $tag, $break)`: more than 12 words and it is hidden (class `crm-help`) until the "?" button of the page is clicked, shorter stays visible. A page calls `crmHelpToggle()` before `llxFooter()`. A warning (`div.warning`), an error, a confirmation or a notice about data leaving (the AI service and its masking) is not an explanation and stays visible. The About tab of the setup screen is page content and stays visible.
- Version and changelog: the only mandatory piece is `$this->version` in `core/modules/modCrm.class.php`, currently `1.2.0`: `1.0.0` and `1.1.0` are released and their sections of `ChangeLog.md` are closed; what is built now is listed in the `1.2.0` section (the changelog is optional for Dolibarr, but displayed on the module help page). Keep the section of the current version up to date with every change a user or an administrator can notice, in the same change. When a version is released, add the next version above it (`## 1.1.1`, `## 1.2.0`...) and set `$this->version` to it; a change of schema or of rights is at least a minor version. Dolibarr keeps no module version in the database and has no module upgrade mechanism, hence the schema steps. From 1.2.0 on, every feature that changes an interface or the data is documented in `doc/USER_GUIDE.md`, `doc/ADMIN_GUIDE.md` and `doc/STRUCTURE_ANALYSIS.md` marked "From v1.2.0" (the same for later versions), so the guides do not present it as present from the start.
- The sender of an e-mail written in `email_compose.php` is chosen among `crmSenderChoices()` (default, user e-mail, lead collector mailbox). The form posts a code, never an address: the server resolves it (`crmSenderChoiceFor()`), so only listed addresses can be used. `crmSendMail()` takes the sender and falls back to `crmSender()` for anything that is not an address. Outreach and reminders always use `crmSender()`. The last choice is kept in the user parameter `CRM_MAIL_FROM_CHOICE`.
- Every e-mail step run by an outreach writes a journal line with the message as built (`Sequence::buildEmail()`), whatever the outcome, and the day of a line is `crmSequenceDay()` from the enrolment date. The journal is shown on the outreach card and on the deal card, and `sequence_log_view.php` opens one message; see "Journal of the outreach" in `doc/STRUCTURE_ANALYSIS.md`. Schema version 2 added the content columns.
- Two hourly cron jobs: owner reminders (on, dry-run on by default) and automated outreach (off, dry-run on by default). Mail goes to the deal contact, never to the company address.
- Visibility: without `readall`, users see only deals where `fk_user_resp` is themselves (`crmOwnerSql()`, `crmCanReadOwner()`). This applies to UI, cron and MCP alike.
- Disable never drops `llx_crm_*` and never deletes events. Seeds run only when the entity has no pipeline.

## Layout

```text
core/modules/modCrm.class.php   Descriptor: rights, menus, cron jobs, box, hooks, init()/remove()
core/boxes/crmwidget.php        Home box (overdue steps, deals without next step)
class/                          Domain classes: Opportunity (extends CommonObject), Pipeline, Stage,
                                Qualification, Outreach, CrmActivity, CrmReport, CrmCron, ActionsCrm (hook)
class/mcp/                      MCP tools: CrmMcpTool (base) + Dictionary / Opportunity / Activity /
                                Outreach / Report tools. Registered in class/actions_crm.class.php
lib/crm_bootstrap.inc.php       First include of every page: locates and loads main.inc.php
lib/crm.lib.php                 Helpers needing Dolibarr (rights SQL, mail, constants, seed, dictionaries, refs)
lib/crmlogic.lib.php            Pure rules, no Dolibarr (placeholders, score, due date, rotting, weighted)
index.php pipeline.php opportunity_{list,card}.php activity_list.php sequence_{list,card}.php report.php
admin/setup.php                 Settings, pipelines/stages, qualification, dictionaries
js/pipeline.js css/crm.css      Kanban drag and drop (posts with CSRF token), styles; no third-party script
sql/llx_crm.sql                 Single schema file, indexes inline, no IF NOT EXISTS, no .key.sql
langs/<locale>/crm.lang         en_US and fr_FR are the maintained ones; the other locales of Dolibarr are machine translations
test/phpunit/CrmLogicTest.php   Tests for the pure logic lib (no Dolibarr)
test/cli/*_check.php            Checks that need Dolibarr and a database, in a transaction rolled back
```

Pages start with `require_once __DIR__.'/lib/crm_bootstrap.inc.php'` (needed because the real path is outside `htdocs`, so a relative include of `main.inc.php` fails) and then call `crmStartPage()`, which loads langs, refuses a disabled module and checks the read right.

## Conventions

- `declare(strict_types=1)` in every PHP file. PHP 8.1 compatible syntax only.
- **Tabs** for indentation. Dolibarr style: Allman braces for classes and methods, `if (...) {` on the same line otherwise, `array(...)` rather than `[]` is the dominant style here; match the surrounding file.
- Keep actions and view apart in pages. Business logic (stage moves, closing, qualification, sending, reminders) lives in the classes so pages, cron and MCP tools call the same methods. Do not duplicate rules in a page or a tool.
- Put rules that need no Dolibarr in `lib/crmlogic.lib.php` so they stay unit-testable.
- SQL: use `MAIN_DB_PREFIX`, cast ints, `$db->escape()` strings, filter by `entity`. Schema changes go in `sql/llx_crm.sql` (new installations) and in a numbered schema step (existing ones), see "Schema" above.
- Stages, qualification items, sources and loss reasons are edited and turned off in `admin/setup.php`, never hard-deleted when in use (`crmItemUsage()`, `crmDeleteItem()`, `Stage::delete()` refuses deals and history). Reads for choice lists filter on `active`; reads that display what a deal already points at must not (see "Retiring instead of deleting" in `doc/STRUCTURE_ANALYSIS.md`). Destructive icon links go through `Form::formconfirm()` (`askdel...` shows it, `confirm_del...` acts). `crmSave*` take `active = -1` to keep an existing flag.
- Seeded entries (pipeline, stages, sources, loss reasons, qualification items) are stored in English and translated at display time by `crmDictLabel()`, which matches the seed's English label, so a renamed or custom entry stays as stored. Show every such label through it, and when you add a seed entry add its key to the map in `lib/crm.lib.php` and to both lang files. MCP tools return the stored label.
- The on/off settings of `admin/setup.php` are switches handled by the page itself (action `toggle` by ajax, `set_<CONST>`/`del_<CONST>` as links), not by Dolibarr's `constantonoff.php` ajax, which is for administrators only while the Setup screen needs only "Configure CRM". A new boolean setting goes in the `$switches` list; it is stored as 1 or 0, never deleted, because `crmEnsureConstants()` recreates a deleted constant with its default.
- Buttons are `<input type="submit|button" class="button" value="Label">` or `<a class="button">`, like Dolibarr's own, never `<button class="button">`: the theme styles `input.button` and `a.button` only (`#mainbody input.button`, `theme/*/global.inc.php`), so a `<button>` keeps the browser's relief look. The value of an input is its label, so several submit buttons of one form each get their own name (`act_save`, `act_send`...) and the page derives the action from the one posted. Scripts change the label with `.value`. Tab switchers and the "?" toggle are `<button>` on purpose, styled flat in `css/crm.css`.
- Output gotchas: `dol_escape_htmltag($text)` turns newlines into a literal `\n`; for text areas and multi-line text use `dol_escape_htmltag($text, 0, 1)`. Plain-text input (an e-mail body, a subject) is read with `GETPOST(..., 'nohtml')`: `restricthtml` turns `&` into `&amp;` and `alphanohtml` drops quotes.
- Every user-visible string goes in `langs/en_US/crm.lang` and `langs/fr_FR/crm.lang`, which are maintained by hand. The other `langs/<locale>/crm.lang` files are machine translations of en_US, never reviewed by a native speaker: a missing key there simply shows English (Dolibarr falls back to en_US), so a new key may be left out until someone retranslates (as of 1.1.0 every locale has every key; `test`-style check: compare the keys of each `langs/<locale>/crm.lang` with `en_US`). A variant locale (`de_AT`, `fr_BE`, `es_MX`...) has no directory of its own when Dolibarr falls back to `xx_XX` (the `de_DE` file); only `ar_*`, `bn_IN`, `el_CY` and `zh_HK` are copies. Key style: `CrmSomething`. An error set by a class is a language key `CrmError...` and is shown through `crmErrorText()`, never as an English literal.
- Security rules (details in "Security design" of `doc/STRUCTURE_ANALYSIS.md`): call `crmRequireToken($action, $displayActions)` on every page with actions and give each form and action link a `token`; pass a request id through a query that adds `crmOwnerSql()` and the entity, never alone; put business rules in the class (`Sequence::enrol()`, `Opportunity::validateLinks()`, `Stage::validate()`), not in a page; escape every label where it is printed, including titles and `formconfirm()` texts (`trans()` keeps markup in its arguments); clean MCP input with `argString()` (single line), `argText()` and `argBody()`; show a database error through `crmDbError()` and `crmErrorText()`, never `$db->lasterror()`; a new setting goes through `crmNormalizeSetting()`; a new class file starts with the `DOL_DOCUMENT_ROOT` guard. Never write a password, key or host name into the repository.
- Do not add third-party JS/CSS libraries. Do not add a REST API, a private activity table, a scoring-rule engine, or a custom app shell (see "Out of scope" in `doc/STRUCTURE_ANALYSIS.md`).
- MCP tool names start with a verb. Dolibarr's tool access screen (`ai/admin/configure_tools.php`) labels a tool "Modify" when its name starts with `create`, `update`, `delete`, `add`, `remove`, `change`, `write`, `edit`, `validate`, `pay` or `send`, and its "View only" preset allows every other name. So a tool that writes must start with one of those verbs (`change_crm_opportunity_stage`, `send_crm_owner_reminders`, `create_or_update_crm_stage`) and a read tool with `list_` or `get_`; the name before that rule was `crm_<verb>_...`, which made every tool look read-only. `test/cli/mcp_tools_registration_check.php` enforces it on a 25 core.
- MCP tools: read tools return `NO_WRITE`; write tools return `writeConfirmationPreview()` text naming the record; `getRequiredRights()` must match the permission table; owners are numeric user ids (there is no user search tool). Add a new tool class to `ActionsCrm::addMcpTools()` and to the tool table in the docs.
- Adding a right means a new entry in the descriptor with the next id (`10480109`...). Existing instances only pick it up after the module is disabled and re-enabled.
- Internal notes (from v1.2.0): `CrmNote` (`class/crmnote.class.php`) owns notes, revisions (`llx_crm_note_revision`: the previous text, with its author and date, is saved on every edit) and files (`llx_crm_note_file`, stored under `<documents>/crm/opportunity/<deal id>/`). The deal `description` column is no longer used once `CrmNote::supported()`; rights are checked inside the class (`readableDeal()`, `canEdit()`), never only in a page or tool. Files are served by `note_file.php` only, never by a public link. MCP tools are in `CrmNoteTool`; the write-tool count in `mcp_tools_registration_check.php` must follow. Schema version is 4.
- Prospect tab of the third party (from v1.2.0, `comm/card.php`, hook context `thirdpartycomm`; the Third party tab, `thirdpartycard`, is left alone on purpose): `ActionsCrm::formObjectOptions` for the "CRM opportunity" row, `addMoreRecentObjects` for the "CRM history" block, `CrmAccountView` for the data, `account_history.php` for the full list. Never patch core.
- The general search box gets a CRM entry from the hook `addSearchEntry` (context `searchform`, `ActionsCrm`), which links to `opportunity_list.php?status=all&search_all=<text>`. Dolibarr lists core modules itself and external modules only through that hook.
- Hook contexts are declared in `module_parts['hooks']` and stored in the constant `MAIN_MODULE_CRM_HOOKS`; a new context needs a re-enable (or an update of that constant). Register only the context a method needs: the collector calls `doCollectImapOneCollector` for both `emailcolector` and `emailcollector`, and CRM registers only the second, so a message is not processed twice.
- Descriptor changes (menus, cron jobs, rights, box) apply only on re-enable: Home → Setup → Modules → CRM (off then on), or via the DB/CLI. Re-enable is safe: tables, deals, constants and events are preserved.

## Verifying changes

1. Syntax: `php -l path/to/file.php` for every touched PHP file (PHP 8.3 locally).
2. Database checks: `php test/cli/setup_lists_check.php /path/to/dolibarr/htdocs` and `php test/cli/next_steps_and_lists_check.php /path/to/dolibarr/htdocs`, `php test/cli/mail_sender_check.php /path/to/dolibarr/htdocs`, `php test/cli/sequence_journal_check.php /path/to/dolibarr/htdocs`, `php test/cli/deal_outreach_check.php /path/to/dolibarr/htdocs`, `php test/cli/ai_time_limit_check.php /path/to/dolibarr/htdocs`, `php test/cli/reply_stage_check.php /path/to/dolibarr/htdocs`, `php test/cli/mail_contact_match_check.php /path/to/dolibarr/htdocs`, `php test/cli/account_view_check.php /path/to/dolibarr/htdocs`, `php test/cli/notes_check.php /path/to/dolibarr/htdocs`, `php test/cli/security_check.php /path/to/dolibarr/htdocs` and `php test/cli/mcp_tools_registration_check.php /path/to/dolibarr/htdocs` (run the last one against a 24.0.0 extract as well as the main install). `DOLIBARR_HOST` sets the host name and `DOLIBARR_HTDOCS` the path. They need the module enabled, run as user 1, print PASS or FAIL per check, exit 1 on a failure, and roll back everything. Add a check there when you change a rule that touches the tables; share the start through `test/cli/crm_cli_bootstrap.inc.php`.
3. Pure logic tests: `test/phpunit/CrmLogicTest.php` does not load Dolibarr. The installed `phpunit` requires PHP 8.4 and fails here; run the assertions with another PHPUnit (e.g. a phar compatible with PHP 8.3) or a throw-away script that requires `lib/crmlogic.lib.php`.
4. In the browser or with curl against http://my.dolibarr.net: log in as `admin` (the login form needs the `token` hidden field from `index.php`; send `actionlogin=login&loginfunction=loginfunction`), then open `/custom/crm/...`. Watch `/var/www/dolibarr/documents/dolibarr.log` and the PHP error log for warnings, since dev mode shows them.
5. For the kanban or other JS-heavy pages, drive a real browser; curl cannot check drag and drop.
6. For cron and outreach, keep `CRM_DRY_RUN` and `CRM_REMINDER_DRY_RUN` on while testing. Never switch dry-run off on this instance without telling the user: it sends real e-mail to deal contacts.
7. For MCP: the AI module must be enabled, the tool must pass `AI_MCP_SERVER_ALLOWED_TOOLS`, and the user needs the matching `crm` right (and `Read own deals` at least).

Test data created on the dev instance (deals, outreach, agenda events) is real data in a shared DB: clean up what you create, and do not touch core objects you did not create.

## Known gaps and traps

- The files of the notes go to `<documents>/crm/opportunity/<deal id>/` (here `/var/www/dolibarr/documents/crm`), and the CLI checks create that folder as the user who runs them. A folder owned by that user and closed to the web server (`drwxrwx---`) makes every web upload fail with "Le fichier n'a pas pu être écrit" / `ErrorDirNotWritable`. After running `test/cli/notes_check.php`, check the owner and rights of `documents/crm` (the instance uses `chmod 777`, as its other folders there), or run the checks as the web server user.

- `doc/STRUCTURE_ANALYSIS.md` is the design record. When behaviour changes, update it in the same change, together with `doc/ADMIN_GUIDE.md` (anything an administrator sets, installs or checks), `doc/USER_GUIDE.md` (anything a salesperson sees or does) and this file if setup facts move. `README.md` stays a short overview: do not grow it again.
- No purge action (explicitly deferred in the design doc).
- Multi-currency is not supported; amounts are in the company currency.
- Reply detection is manual ("prospect replied" on the card or by MCP); the module never reads a mailbox.
- Locales other than English and French are machine translations, not reviewed.
- The tests directory is not part of the Dolibarr core suite. `test/phpunit` stays free of Dolibarr; `test/cli` is the place for checks that need Dolibarr and a database.
